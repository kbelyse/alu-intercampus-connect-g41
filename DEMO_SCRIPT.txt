[ON SCREEN: Navigate to Settings and log out so the app goes back to splash.
Then walk through: Splash → Onboarding screens → Interest selection → Login.
Have VS Code open side-by-side at app_colors.dart or app_typography.dart

Thanks. So I want to talk about the design decisions we made, because I think
this is where a lot of our work went.

Let me start from the very beginning — the splash screen. We wanted the first
thing a user sees to feel premium, not generic. So we built this animated
splash with two floating gradient orbs — one in the secondary purple color and
one in our primary orange — that scale up and down in opposite rhythms. The
logo comes in with a spring animation, and then the tagline fades in below.
This kind of layered animation entry is directly inspired by how Apple builds
app launches, where every element has intentional timing.

[Navigate to onboarding]

Now the onboarding — we have three slides. Discover, Connect, Grow. But the
thing I want to point out is the third slide, which is the interest selection
screen. This isn't just a pretty screen — these interests that the user picks
actually feed directly into our recommendation engine. So from the very first
interaction the user has with the app, we're already personalizing their
experience. That's a deliberate product decision, not just a UI choice.

[Show interest tags being selected]

Notice how when you tap an interest, it transitions smoothly between the
unselected state — grey border, grey text — and the selected state — orange
border, orange background, orange text. Everything uses `AnimatedContainer`
with a 200ms duration. It's subtle but it makes the interaction feel alive.

Now let me talk briefly about our design system.

[Open app_colors.dart]

We have six defined colors: background at 0A0B14, which is a very deep navy-
black. Surface at 12141F, which is slightly lighter. Elevated at 1A1D2E for
floating cards. Primary orange at F5A623, secondary purple at 6C63FF, and then
success green and error red. This three-layer depth system — background,
surface, elevated — is what gives the app that sense of cards floating above
the background without needing any actual shadows.

[Open app_typography.dart]

For fonts we use two families — Space Grotesk for headings and Inter for body
text. Both loaded through google_fonts, so no bundled assets needed. Space
Grotesk has that slightly geometric, modern look that makes headings feel
designed, not just typed. Inter is the most legible UI font that exists right
now — it's what Linear, Notion, and most modern SaaS products use.

Every text style is pre-defined in AppTypography — displayLarge down to
caption. So no hardcoded font sizes anywhere in the codebase. This was
deliberate for maintainability and consistency.

I'll pass to Placide who'll talk about the technical architecture underneath
all of this.

SEGMENT 3 — PLACIDE  |  STATE MANAGEMENT + CODE ARCHITECTURE
Duration: ~2.5 minutes  |  SHOW: Live code in lib/shared/providers/ and models/
================================================================================

[ON SCREEN: VS Code showing the project structure — lib/ folder expanded.
Show: user_provider.dart, communities_provider.dart, then show a model file.
Then LIVE in the app show the RSVP interaction and join community interaction.]

Okay so I want to talk about how we structured the code because I think this
is one of our strongest areas.

[Show folder structure]

We used a feature-first architecture. So every feature — home, communities,
chat, profile — lives in its own folder under lib/features. Each folder can
have screens, widgets, and if it needs something feature-specific, it has that
too. The shared things — models, providers, widgets that are used across the
whole app — live under lib/shared. This is the pattern used in production
Flutter applications and it makes the codebase very maintainable.

[Open user_provider.dart]

For state management we used Riverpod 2 with StateNotifier. This is the current
recommended approach for Flutter apps. Let me show you what this actually looks
like in practice.

The UserNotifier class holds the current user's state. Every action — RSVPing
an event, saving an event, joining a community — is a method on this notifier.
So when a user RSVPs to an event, we call `rsvpEvent`, which adds the event ID
to their rsvpedEventIds list, increments eventsAttended, adds 10 leadership
points, and calls setState with a copyWith — which is the immutable state
pattern.

[Show in app: tap RSVP on an event]

Watch this — I'm on the event details screen for the ALU AI Summit. When I tap
RSVP Now, you can see the button immediately changes to "Cancel RSVP" in the
elevated grey, and the green RSVP'd badge appears in the bottom right of the
hero image. That's because the UI is watching the userProvider reactively via
Riverpod's Consumer widget. No setState calls in the UI — the data flows down
automatically.

[Open communities_provider.dart]

The CommunitiesNotifier is interesting because it cross-notifies. When you join
a community, it updates both the community's member count and the user's
joinedCommunityIds. Both happen atomically so the UI stays consistent.

[Show join community in app]

See — tapping Join on a community immediately updates the button to "Joined",
the member count increments by one, and on the home screen the trending
communities section reflects this.

[Open event_model.dart]

Our models use immutable value objects with copyWith patterns. Every model has
a copyWith method, which means state updates never mutate — they always return
new instances. This prevents subtle bugs where one part of the app
accidentally changes shared state.

Passing to David who'll show the navigation and key feature flows.

Okay so I want to talk about the feature I'm most excited about — the AI
Recommendation Engine — and then close out with our version control approach.

[Point at Recommended For You on home screen]

This section — "Recommended For You" with the AI Powered badge — is a
frontend simulation of a real recommendation system. I want to be honest about
what it is: it's not calling an external API, it's running locally using state.
But the algorithm is real and it does actually adapt.

[Switch to VS Code → recommendations_provider.dart]

Here's how it works. The `recommendedEventsProvider` takes three inputs: the
current user, all events, and the user's joined communities.

For each event it calculates a relevance score:
- If an event's category directly matches one of your interests: plus 3.0
- If an event's category matches something you've previously RSVP'd to: plus 1.5
- If an event's category matches a tag in one of your joined communities: plus 1.0
- If the event is featured: plus 2.0
- Popularity factor from attendee count, and a recency bonus for events in the next 14 days

Then it sorts all events by this score, filters out ones you've already RSVP'd
to, and returns the top 6.

[Switch back to app, RSVP to an event from the recommendations]

Watch what happens when I RSVP to the Founder Fridays event. I go to the
details screen, tap RSVP Now... and now go back to the Home screen. The
recommendations have updated. Founder Fridays is gone — because you've already
committed to it — and the events in Entrepreneurship and Finance have moved up
because the engine now knows you're interested in that category.

That's the personalization loop working. The more you interact, the more
relevant your feed becomes. In a production version this would be a server-side
model with collaborative filtering. As a frontend prototype it demonstrates the
concept fully.

TIPS FOR RECORDING
================================================================================

1. Use an Android emulator at 1080x1920 (Pixel 5 API 34) for clean recording
2. Set system font size to default, no accessibility fonts
3. Record at 60fps if possible — animations look much better
4. Have the VS Code font at 16px minimum so code is readable on video
5. Don't rush — pause 1 second after each navigation tap before speaking
6. If something doesn't load (network image), just keep talking — say
   "you'd see the event cover image here, it's loading from Unsplash"
7. Each person should record their own segment in one continuous take
   if possible, then stitch in post-production
8. Put a subtle title card between each person: "Mordecai — UI/UX Design"
